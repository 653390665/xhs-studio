# 采集操作规范

> 这份文档不是建议，是**硬约束**。
> 它的起因是 2026-10-28 的一次真实事故：绕过限速抓 294 篇详情，账号被风控。

---

## 0. 一句话原则

**防线不能依赖调用方的自觉。**

任何「记得加 sleep」「记得检查限速」的要求，都会在某个赶时间的下午被跳过。
所以本项目的约束都做在**代码层**，而不是纪律层。本文档只做两件事：

1. 说明代码已经强制了什么（不用你操心）；
2. 说明代码管不到、必须人守的部分。

---

## 1. 代码已经强制的（不用你操心）

### 1.1 请求频率（adapter 层，绕不过）

`backend/app/adapters/xhs/pc_api_adapter.py` 的每个平台方法都会先调 `_pace()`：

```python
def _pace(self, action):
    get_crawl_guard().acquire(self._budget_key, action)
```

`acquire()` 是**阻塞式**的：超出预算就等，等不到就抛 `CrawlThrottled`，
绝不静默超发。

当前限额（`crawl_guard.ACTION_LIMITS`）：

| 动作 | 限额 | 对应方法 |
|---|---|---|
| `profile_page` | **2 次/分钟** | `get_user_notes` / `get_user_notes_page` / `get_user_info` |
| `note_detail` | **10 次/分钟** | `get_note_info` / `get_note_comments` |
| `search` | **2 次/分钟** | `search_note` |

**这些数字来自实测，不是估计：**

```
2026-10-28 14:50–15:10   140 篇 / 14.4 分钟 = 9.6 次/分钟
                         完整跑完，正文 100%          ← 实测可用
2026-10-28 22:0x         ~28 次/分钟
                         会话中途失效                  ← 实测失败
```

`note_detail` 定在 10（已验证值），不是定在更低的 3。
**低于实测可用值不是谨慎，是没有依据的假设**——上一版把它定成 3，
把一件 8 分钟的事拖成了 7.5 小时。

如果要改这个数字：先补一个新的实测数据点，再改。否则测试会拒绝
（`test_note_detail_limit_is_evidence_backed` 要求 9 ≤ 值 < 28）。

**这个限额对谁都一样**：界面、调度器、智能体、临时脚本，走同一个 adapter
就受同一套预算。

### 1.2 分桶依据是 cookie 指纹，不是账号 ID

```python
self._budget_key = "cookie:" + sha256(cookies)[:16]
```

原因：
- adapter 构造时只有 cookies，不知道 account_id；
- 「哪个登录态在发请求」才是平台侧风险的真正来源；
- 不依赖调用方正确传参——这正是事故的教训。

换 cookie（重新登录）会换桶，等于重置计数。这是合理的：重新登录本身就是
一次人工介入。

### 1.3 单次运行总量上限

```python
MAX_ITEMS_PER_RUN = 20
MAX_NOTES_PER_BATCH = 20   # 一次 batch-save 的上限，与上面一致
```

**2026-11-27 从 150 下调到 20。** 理由不是"听起来保守"：

- 150 那一轮（140 篇 / 14.4 分钟）技术上跑完了，但把账号连续暴露在平台上
  十几分钟，而且远超用户实际需要；
- 用户的真实用法是「搜一页、挑几篇、翻下一页」；
- 按 20 条切，每批都是一个短会话；**批与批之间是用户翻页的自然停顿**，
  比程序里 sleep 5 分钟更像人在操作。

`MAX_NOTES_PER_BATCH` 是配套的：**采集深度定在 20，保存入口就不能允许
一次塞 100 条**，否则限额被旁路。

### 1.3.1 批间隔

```python
SESSION_PAUSE_MINUTES = 5
```

**这跟下面的 30 分钟冷却不是一回事。** 30 分钟冷却针对「重复抓同样的列表」，
补正文是「继续没做完的任务」，不该付那个代价（那会把 8 分钟的事变成 7.5 小时）。

5 分钟只为了防止连续冲刺，是保守估计，没有实测依据——如果觉得慢，
应该缩小批次而不是取消它。

### 1.3.2 前端也在配合深度

| 参数 | 值 | 位置 |
|---|---|---|
| `DETAIL_CONCURRENCY` | **1**（原 3） | `pages/Materials.tsx` |
| `AUTO_PREFETCH` | **3**（原 6） | `lib/searchSession.ts` |
| detail 请求超时 | 25 秒 | `lib/notesCache.ts` |

并发从 3 降到 1 的原因：adapter 已经把 `note_detail` 限到 10 次/分钟并加了
抖动，再叠 3 路并发只会让三个请求一起排在 guard 队列里，然后前端 25 秒超时全挂。
串行时每个请求都能拿到自己的节奏。

`acquire` 的 `max_wait` 也从 90 秒降到 **40 秒**：前端 25 秒就 abort 了，
后端等更久只会产生「用户已看到失败、请求才发出去」的浪费。

### 1.4 账号冷却

```python
ACCOUNT_COOLDOWN_SECONDS = 30 * 60
```

同一个账号 30 分钟内重复采集会被拒绝。理由：**同一账号连续翻页是最明显的
机器人特征，而且通常没意义**——数据没变。

### 1.5 失败状态必须诚实

`classify_failure()` 只返回这几种，**永远不会返回 `ok`**：

| 状态 | 含义 |
|---|---|
| `throttled` | 被限流/风控，可重试 |
| `deleted` | 笔记已删除 |
| `empty_body` | 抓到但无正文 |
| `failed` | 其他失败 |

**限流绝不能写成 0 数据。** 这条是硬规则：把「没采到」记成「采到了但都是 0」，
会让人以为内容不行，实际是采集没成功。

### 1.6 连续风控自动停止

```python
MAX_CONSECUTIVE_THROTTLES = 3
```

连续 3 次被风控就停整轮，而不是「再试一次」。

## 2. 代码管不到、必须人守的

### 2.1 不要写绕过 adapter 的脚本

**这是事故的直接原因。**

我当时写的脚本长这样：

```python
# ❌ 错误：直接调 adapter 的底层 api，绕过 _pace()
adapter = XhsPcApiAdapter(cookies)
api = adapter._api()              # ← 拿到原始 API 对象
api.get_user_note_info(...)       # ← 完全不受限速约束
```

正确做法只有两种：

```python
# ✅ 走 adapter 方法（受限速）
adapter.get_note_info(url)

# ✅ 走 HTTP API（受限速 + 有权限检查 + 有落库）
POST /api/xhs/pc/notes/detail
```

**判断标准**：如果你写 `adapter._api()`，就已经绕过防线了。
`_api()` 前面的下划线不是装饰。

### 2.2 不要在验证时"先快一点看看"

事故发生的具体过程：为了「快速验证 19 条假设能不能用」，我一次拉了 294 篇。

代价对比：

```
省下的时间：约 40 分钟（294 篇 × 2 秒 vs 受限于 3 次/分钟）
付出的代价：账号风控 1–3 天 + 294 条数据白抓 + 登录重来
```

**任何"先快点验证一下"的想法，都应该先算这笔账。**

### 2.3 数据量要分批，不要一次拉全

即使限速会保证频率，**总量**仍然要控制：

```
单次运行：≤ 20 条（约 2 分钟）
批间隔：≥ 5 分钟（或等用户翻页）
每日总量：建议 ≤ 60 条（无代码强制，靠自觉）
```

20 条一批的节奏是「搜一页 → 挑几篇 → 翻下一页」，和真人刷小红书一致。

**不要为了「一次补全」设一个很大的目标，再配一套很慢的节奏。**
上一版就是这样：为 294 篇排了 15 批 × 30 分钟冷却 = 7.5 小时。
正确做法是先采 20 篇（够看一页、够蒸馏），不够再翻下一页。

### 2.4 判断"是不是被风控了"的正确方式

**错误信号**（我这次踩的坑）：

```
{success: true, code: 0, msg: "成功", data: null}
```

这个响应看起来完全成功。它可能的含义：

- 作者 ID 不对（**我这次是这个**，抄成了 22 位，真实 24 位）
- 该账号确实没有公开笔记
- 被风控但平台仍返回成功壳

**正确做法**：

1. 先用 `user/me` 探测登录态（`XhsPcApiAdapter.get_self_info()`）；
2. 检查 ID 长度（24 位十六进制，代码已加校验）；
3. 只有以上都正常、且多个不同账号都返回 null，才怀疑风控。

### 2.5 风控后的处置

```
1. 立刻停止一切请求（包括"探测一下好了没"）
2. 不重试、不换号、不换 IP 绕过
3. 等 24–72 小时
4. 重新扫码登录
5. 第一次只发 1 个请求验证登录态，不要直接恢复大批量采集
```

**「探测一下好了没」本身就是新请求。** 我这次在报错后又跑了 6 个诊断脚本，
每次都加重了风控。

## 3. 检查清单（写采集脚本前逐条过）

```
□ 我是否只调 adapter 的公开方法，没有碰 adapter._api()？
□ 单次运行是否 ≤ 60 条？
□ 如果超过 60 条，是否拆成多批且间隔 ≥ 30 分钟？
□ 同一账号是否在 30 分钟内已经采过？
□ 我是否在抓之前用 user/me 确认过登录态？
□ 失败时我是否会区分 throttled / deleted / empty_body，而不是一律记 0？
□ 我是否准备好了"被风控就立刻停"的退出路径？
```

任何一条答"否"，就不要开始。

## 4. 限额是怎么定的（改之前先读这段）

当前值：`profile_page 2` / `note_detail 10` / `search 2`。

**`note_detail` 是实测值，不是估计值**：

| 值 | 依据 |
|---|---|
| 9.6 次/分钟 | 2026-10-28 实测跑通：140 篇 / 14.4 分钟，正文 100% |
| **10 次/分钟** | 当前值，对齐上面这个已验证数据点 |
| 28 次/分钟 | 2026-10-28 实测失败：会话中途失效 |
| 3 次/分钟 | 曾经的错误值，纯属猜测，把 8 分钟拖成 7.5 小时 |

**这些数字仍然不是精确的安全线。** 平台的阈值不公开、会变，而且
`profile_page` / `search` 只有经验值，没有对应的实测记录。

原则有两条，互相制约：

1. **不要超过实测失败的值**（28/分钟）。
2. **不要低于实测成功的值**（9.6/分钟）——低于它不叫谨慎，叫没有依据。
   一个没人能解释的数字，会在某天被另一个没人能解释的数字替掉。

如果要调整，必须先回答：**你用什么数据支撑这个新值？**
现有测试 `test_note_detail_limit_is_evidence_backed` 会强制
`9 ≤ note_detail < 28`，改之前先补数据点。

## 6. 事故记录

完整复盘见 `docs/PRODUCT_POSITIONING_AND_PLAN.md` §1.7.31。

核心事实：

```
时间：2026-10-28
请求：15 分钟内 328 次
违规：抓详情 29 次/分钟（限额 5），列作品 30 次/分钟（限额 2）
后果：账号被风控，登录态失效，294 条标题白抓，正文 0 条
根因：脚本直接调 adapter._api()，完全绕过 API 层限速
修复：限速下沉到 adapter，阻塞式，不能用布尔返回值忽略
```
